# Independent relay pair draw before each MLP match

The owner explicitly confirmed that each team draws its own independent order. For a three-player relay the allowed pairs remain AB, BC and CA; each appears exactly once per team's match. A single pre-match action draws and persists both independent permutations. Identical orders can occur by chance. Positions still resolve from actual unique player skill grades, or confirmed entered order for repeated grades; no grades or member positions are changed.

An authenticated match endpoint generates both orders on the server, persists them with a timestamp, increments the match version, records an audit entry and notifies clients. Admin/BTC or the assigned referee can draw. Drawing and redrawing are allowed only before any match scoring/history, and require current match version. Draws are serialized against point entry, assignment/member changes and concurrent draws. A recorded order belongs to its actual match participants; participant replacement before play clears stale orders. Already started legacy matches retain AB/BC/CA and cannot be silently reshuffled.

For new/unstarted three-player MLP matches, point entry is blocked until both orders have been drawn. All three legs use the existing shared score thresholds (9 and 18 in the current 27-point format); the two sides can field different pair codes at each leg. Scoring, last-point-on-serve, set results, standings and independent Serie A/B advancement remain unchanged. Orders survive refresh, Undo, score reset and match completion; replaying an existing scored match retains its order.

BTC and referee consoles show a draw button before play and all three pairings with actual player names. The current and next-pair banner identifies both sides independently, including mixed pair codes. Serving-player highlights follow the selected pair order. Public match/court/tournament views show persisted pair identities; awaiting-draw screens do not invent AB as a confirmed draw. Completed views keep full team names and final points. Public pages have no draw controls.

Persistence contract: nullable `relay_order_a`, `relay_order_b` JSON arrays and `relay_drawn_at` on matches; public/admin/scoring state exposes `relayOrderA`, `relayOrderB`, `relayDrawnAt`. Endpoint `POST /api/matches/:id/relay-draw`, body `{expectedVersion}`; response is refreshed match state. Three-player relays only; four-player and non-relay formats retain behavior. Null fields for started legacy matches mean the previous fixed order. D1 and PostgreSQL implementations must match; Preview follows the same user-facing flow.

Tests: all six valid permutations; independent draws including identical outcomes; per-match persistence; no points before draw; stale/concurrent requests; roles/scope; draws refused after point/Undo/reset/finish; participant replacement invalidation; different A/B names and service at 0/9/18; refresh; final scores/champions; public controls absent; existing active real match unchanged. Deployment uses normal migration and assets with updated cache versions, followed by read-only production verification.
